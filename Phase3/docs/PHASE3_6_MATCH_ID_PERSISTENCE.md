# Phase 3.6 — Durable Match History Identifiers

## Problem

The C++ server keeps `nextMatchId` in process memory and initializes it to `1` when the server starts. Phase 3 previously used that value as the SQLite `matches.match_id` primary key. After a C++ restart, a newly created `MATCH 1` could replace an older row with the same identifier, corrupting match history and potentially breaking active-match references.

## Resolution

Phase 3 now has two identifiers with distinct responsibilities:

- `match_id`: generated by SQLite and used by the API, frontend, match-history table, and end/cancel endpoints. This identifier remains monotonic across C++ process restarts while existing history rows are retained.
- `cpp_match_id`: the local identifier returned by the C++ matchmaking process. It is retained for protocol traceability and may repeat after a C++ restart.

The API inserts a new match row without supplying the primary key, then uses the SQLite-generated ID for session-player active-match locks. It no longer uses `INSERT OR REPLACE`, so an old record cannot be overwritten by a repeated C++ ID. Existing databases receive an additive migration that copies each historical `match_id` into `cpp_match_id`.

## Verification

Regression tests verify that:

1. Existing match rows migrate without losing their previous identifier.
2. Completing a match releases its participants from the active-match lock.
3. Reusing C++ match ID `1` after a simulated server restart creates a second API/history row instead of replacing the first.
4. The HTTP session → queue → match → end → re-queue → match → history flow returns distinct durable API IDs even when the simulated C++ process reuses its local ID.

## Operational note

Use the API `match_id` for operator actions and match-history references. Treat `cpp_match_id` as diagnostic metadata only.
